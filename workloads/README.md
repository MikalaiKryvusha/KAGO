# `workloads/` — собственные нагрузки KAGO

Здесь лежат нагрузки, которыми KAGO грузит видеокарту, и собранные из них бинарники.

## Зачем они свои

У всех зрелых бенчмарков запуск из скрипта продаётся отдельно: у UNIGINE — в Professional, у OCCT —
в Enterprise, у 3DMark — в Professional (`researches/03` §3.1). Бесплатен и скриптуем только
FurMark, но он даёт ровную стопроцентную полку, а андервольт валят **переходы** (`researches/02`
§2). Так что писать своё — дешёвый путь, а не дорогой. FurMark на стенд не пускаем вовсе — ваше
решение, интервью 001, вопрос 2.

## Что здесь есть

| Файл | Форма отказа, которую он провоцирует | Почему такая форма нужна |
|---|---|---|
| `sdc_fma.cu` | **молчаливая порча данных** — цепочка умножений-сложений, ответ проверяется точно | из 57 измеренных программ 37 сначала портят числа и только потом падают |
| `branchy.cu` | **падение** — расходящиеся ветки и погоня по указателям, нерегулярная память | остальные 20 падают; управляющий код валится, счётный — врёт молча |

Переходная форма — не третий файл: это расписание в `stress-tester.mjs`, которое гоняет эти же две
между простоем и полной нагрузкой.

## Бинарники здесь лежат намеренно

`.exe` едет в репозиторий по вашему решению (интервью 001, вопрос 3), чтобы KAGO работал на машине
без CUDA Toolkit. У этого решения один слабый бок: собранный файл — единственное, что нельзя
вычитать глазами. Его закрывает `MANIFEST.json` — sha-256 бинарника, sha-256 исходника, тулчейн
сборки и контрольная сумма, которую прогон даёт на этой карте.

```
npm run workloads:verify    # сверить всё, что записано в манифесте, ничего не собирая
npm run workloads:build     # пересобрать, доказать детерминизм 5 прогонами, переписать манифест
```

Изменили исходник — `verify` покраснеет и скажет, что именно разошлось.

## Если редактор светит красным

VS Code показывает в `.cu` десятки ошибок вида «`cuda_runtime.h` file not found», «Unknown type
name `__global__`». **Это не дефект кода.** Так говорит встроенный анализатор C++, который не знает
про CUDA: у него нет ни путей к заголовкам тулкита, ни понятия о ключевых словах устройства.
Настоящий компилятор — `nvcc` — собирает оба файла без единого предупреждения.

Проверять надо тем, что собирает, а не тем, что подсвечивает:

```
npm run workloads:build     # соберёт и прогонит; молчит — значит всё в порядке
```

Правило шире одного каталога и уже стоило времени дважды за одну сессию: инструмент чтения не есть
инструмент проверки (`EXPERIENCE.md` → EXP-0007).
