# Bug 116 — счётчик ВЕРДИКТОВ считает НАШ потолок глубины как предел рычага. Тот же дефект, четвёртый носитель

**Статус:** 🔴 ОТКРЫТ · **Тяжесть:** S2 (карте не вредит; вредит РЕШЕНИЯМ ВЛАДЕЛЬЦА — это последняя
строка, которую читают после прогона, и агент уже однажды пересказал по такой строке неверный вывод) ·
**Найден:** 2026-09-08 09:21, сессия 90, **прогоном на двойнике**, которым закрывался `bugs/115` AC2 —
не чтением кода.

## Вектор цели

**Тип: Avoid.** Не допустить, чтобы итоговая сводка прогона называла причиной остановки железо там,
где остановила НАША уставка. Хотим: строка вердиктов и документ кривой не могут разойтись — они
считают одно и то же событие одним и тем же именем.

## Симптом — одной строкой

**Один прогон, одна секунда, два разных ответа о четырёх ступенях.**

Документ кривой:
```
2872 МГц закрыта: 1035 мВ, статус «depth-capped»
2857 МГц закрыта: 1025 мВ, статус «depth-capped»
```

Итоговая строка ТОГО ЖЕ прогона:
```
ВЕРДИКТЫ: край найден 0 · остановлено НАШИМ потолком глубины 0 · упёрлось в предел сдвига ±1000 МГц 2
```

**Счётчик «остановлено НАШИМ потолком глубины» показывает НОЛЬ там, где документ записал две такие
строки, а две ступени учтены как предел рычага.**

## Repro (детерминированный, карта НЕ нужна)

```
node automation-engine/engine.mjs --sweep --from 2872 --to 2850 --card virtual --max-depth 30
```

Ожидается: `остановлено НАШИМ потолком глубины 2 · упёрлось в предел сдвига 0`.
Наблюдается: `остановлено НАШИМ потолком глубины 0 · упёрлось в предел сдвига 2`.

Сверка документа двойника той же командой:
```
ДО   : {"stop:untouched":388, "stop:depth-capped":1}
ПОСЛЕ: {"stop:untouched":384, "stop:depth-capped":5}
```
Четыре новые строки — все `depth-capped`, `lever-limited` ноль. Код возврата 0.

## Улики

- Журнал прогона: `benches/runs/twin-2026-09-08T09-21-07-03-00/`
- Документ двойника: `benches/runs/virtual-rtx5070ti.json`, строки 2872 · 2865 · 2857 · 2850
- Свидетель каждой: «остановлено НАШИМ потолком глубины 30 мВ (рычаг достаёт до −260 мВ, глубже мы
  не идём по условию прогона)» — то есть **свидетель, метка и документ согласны между собой; расходится
  ТОЛЬКО счётчик.**

## Причина — гипотеза, НЕ проверенная (слепая починка запрещена до подтверждения)

`statusForOutcome` (`engine.mjs:3447`) спрашивает про `outcome.plan.cappedByOperator` четвёртым
вопросом и возвращает `CURVE_STATUS.DEPTH_CAPPED` — эта ветка работает, что доказано документом.
Счётчик вердиктов, судя по всему, классифицирует исход **своим** разбором, а не читает уже
посчитанный статус строки. Тогда это ровно `PHILOSOPHY.md` → DRY: один факт живёт в двух местах и
они разошлись.

⚠️ **Это гипотеза.** Ветку счётчика надо найти и прочитать до правки.

## Почему это ЧЕТВЁРТЫЙ раз, а не первый

Один и тот же класс — «наше условие прогона записано как предел железа» — уже находили:

| когда | носитель | как лечили |
|---|---|---|
| 2026-08-17 | документ кривой, 54 строки | завели значение `depth-capped`, старые строки не переклеили |
| 2026-08-23 | документ кривой, ось «карта не отдала» | завели значение `not-served` |
| 2026-09-08 (`bugs/115`) | документ кривой, 42 строки | перепрожиг по решению владельца |
| **2026-09-08 (этот тикет)** | **счётчик ВЕРДИКТОВ в сводке прогона** | — |

**Урок класса, теперь с четвёртым подтверждением:** починка ОДНОГО носителя не чинит остальных.
Значение словаря завели один раз, а читателей у исхода оказалось как минимум два — документ и
сводка, — и второго никто не переучил.

## Критерии приёмки

- **AC1.** Счётчик вердиктов и документ кривой не могут разойтись на одном прогоне.
  - Ситуация. Двойник, `--max-depth 30`, полоса 2872…2850 МГц, рычаг достаёт до −260 мВ.
  - Действие. Оператор запускает прогон командой из Repro выше.
  - Результат. Строка ВЕРДИКТОВ печатает «остановлено НАШИМ потолком глубины 2 · упёрлось в предел
    сдвига ±1000 МГц 0», и то же число стоит в документе.
  - Проверка. `node automation-engine/engine.mjs --sweep --from 2872 --to 2850 --card virtual --max-depth 30`
    печатает `остановлено НАШИМ потолком глубины 2`; счёт меток `depth-capped` в документе двойника
    вырос ровно на 2 измеренных строки.

- **AC2.** Счётчик берёт статус СТРОКИ, а не разбирает исход второй раз (DRY: один факт, одно место).
  *Проверка:* в коде счётчика нет собственного разбора `cappedByOperator` / предела рычага —
  он читает `statusForOutcome`.

- **AC3.** Сторож краснеет на сломанной версии.
  *Проверка:* мутация «счётчик классифицирует сам» → сторож красный; снята → зелёный.
  `THREAT` · `PROVED-AGAINST` · `GAP` · `ON-REAL-PATH` объявлены рядом (ворота 5).

- **AC4.** Инвентарь класса: найдены ВСЕ читатели исхода спуска, не только эти два.
  *Проверка:* в тикете список носителей с путями; каждый либо читает `statusForOutcome`, либо назван
  исключением с доводом.
