# Bug 107 — «чёрный ящик» судьи сбрасывается, но НЕ опустошается: каждое срабатывание переписывает всю ленту заново

**Статус:** ✅ **ЗАКРЫТ 2026-09-05 (сессия 85, автономный цикл)** — см. «Починка» в конце ·
**Тяжесть:** S2 — улика не теряется, но дублируется, и приборы, которые её СЧИТАЮТ, считают копии ·
**Найден:** 2026-09-05, сессия 85, при сверке размеров артефактов до и после `plans/88` Ш3 ·
**Класс:** код и комментарий рядом с ним утверждают разное — пара «правда ↔ зеркало» внутри одного
модуля.

## Симптом, снятый числами НА БАЗОВОЙ ЛИНИИ (до правки Ш3)

Репетиция смерти `strangle`, прогон 2026-09-05 09:29:10, файл `fuse-ring.jsonl`:

```
строк 10718 · различных отметок времени 1365 · повторяющихся 1361 · максимум копий одной отметки 8
```

Лента такта записана **7,85 раза в среднем**, а отдельные такты — восемь раз. Каждое срабатывание
дописывает в файл ВЕСЬ ринг целиком, включая такты, уже сброшенные предыдущими срабатываниями.

## Причина — одна строка, и рядом с ней комментарий, который ей противоречит

```js
// fuse.mjs — dumpRing
for (const e of drainRing(ring)) writeSync(rfd, `${JSON.stringify(e)}\n`);
```

```js
// fuse.mjs — drainRing: имя обещает опустошение, тело его не делает
export function drainRing(ring) {
  const out = new Array(ring.filled);
  ...
  return out;                     // ← ни filled, ни next не сбрасываются
}
```

А в `resetForRearm`, двумя сотнями строк ниже, стоит прямое утверждение обратного:

> `ring` — уже опустошён `dumpRing` внутри трипа; повторная чистка была бы второй правдой.

**Комментарий описывает поведение, которого нет.** Именно поэтому дефект и прожил незамеченным:
читатель кода получал ответ на свой вопрос и дальше не смотрел.

## Чем это платит

1. **Разбор читает повторы как события.** `countStallsBeforeTrip(ev.ring)` (`plans/65`, сетка
   `--tune-n`) считает остановы ПО КОЛЬЦУ. Дубли ленты завышают счёт остановов — то есть прибор,
   которым выбирается уставка N, меряет копии.
2. **Артефакт растёт квадратично по числу срабатываний.** Шторм из 27 спасений даёт 27 копий ленты.
3. **Имя функции лжёт вызывающему.** `drainRing` в двух блоках самопроверки проверяет только
   ПОРЯДОК выдачи (`[1,2,3]`, `[3,4,5]`) и ни в одном — опустошение. Ни один блок не краснеет.

## 🔴 Честно: моя правка Ш3 УСИЛИЛА этот дефект, и это названо, а не замолчано

До Ш3 такт судьи ОСТАНАВЛИВАЛСЯ на время спасения, поэтому между срабатываниями в кольцо попадало
мало новых тактов. С Ш3 такт идёт весь рескью, каждое спасение длится на 3 с дольше (окно здоровья),
и кольцо успевает наполниться до потолка (15 000) между срабатываниями. Замер того же профиля
`strangle` после правки: **772 КБ → ~25 МБ** на один прогон репетиции, 27 сбросов по полному кольцу.

Дефект НЕ создан правкой — он показан на прогоне ДО неё числами выше. Но множитель мой, и назвать
его — часть работы.

## Лечение (форма выведена, НЕ применена)

Опустошать кольцо в `dumpRing` — там, где вызывающий уже считает его опустошённым:

```js
const dumpRing = () => {
  ...
  for (const e of drainRing(ring)) writeSync(rfd, ...);
  ring.filled = 0; ring.next = 0;          // ← или это делает сам drainRing
  ...
};
```

И блок, который краснеет: два сброса подряд дают ленту ОДИН раз, а не дважды; плюс мутация «снять
опустошение» обязана его покрасить.

## Почему не чинилось В МОМЕНТ НАХОДКИ (и почему чинится теперь)

Заказ той половины сессии был назван владельцем поимённо — `plans/88` Ш3 и `bugs/101` находка 1, — и
кольцо это **улика после смерти машины**, чей контракт разбирался отдельным тикетом (`bugs/78`).
Менять, что попадает в файл, — правка семантики улики, а не попутная уборка внутри чужой приёмки.
Тикет взят, когда владелец передал работу агенту («давай без меня»), и сделан своим шагом со своими
блоками.

# ✅ ПОЧИНКА 2026-09-05 (автономный цикл)

## Лечение — имя функции стало правдой

`drainRing` называлась «drain», вела себя как «peek», и рядом, в `resetForRearm`, стоял комментарий,
утверждавший обратное. Теперь она действительно опустошает (`filled = 0`, `next = 0`), а комментарий
переписан с пометкой, что до этого дня он был неправдой, — тихо править его было бы вторым сокрытием.

Ячейки буфера намеренно НЕ чистятся: при `filled === 0` они недостижимы и будут перезаписаны, а
обход пятнадцати тысяч слотов — работа в форензическом пути, который обязан быть дешёвым.

## Почему это НЕ потеря улики — и это проверяемо, а не обещано

Объединение всех сбросов до и после правки одно и то же: исчезают ровно повторы. Кольцо как было,
так и осталось буфером фиксированной ёмкости с вытеснением старейшего — что не влезло между двумя
сбросами, терялось и раньше. **Отдельный блок утверждает именно это**, потому что без него
«опустошает» неотличимо от «теряет».

отдаёт только новое» и «объединение всех сбросов ПОЛНОЕ». **Мутация** «снять опустошение» краснит
оба. Батарея проекта: 49 наборов, **2564** зелёных блока, 0 красных.

## Что это чинит у соседей

`countStallsBeforeTrip`, которым сетка `plans/65` выбирает уставку N, считает события ПО КОЛЬЦУ.
До правки он считал копии — то есть прибор выбора порога мерил дубли. Теперь счёт честный.
