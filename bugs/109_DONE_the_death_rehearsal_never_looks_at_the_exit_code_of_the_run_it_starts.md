# Bug 109 — репетиция смерти НЕ СМОТРИТ на код выхода прогона, который сама запускает: убитый по таймауту прогон объявляется зелёным

**Статус:** 🟢 ПОЧИНЕН 2026-09-05, сессия 85 (проверка добавлена, покраснела на том самом прогоне,
что её и вскрыл) · **Тяжесть:** S1 — ложный зелёный в ПРИБОРЕ ПРИЁМКИ, то есть в том, чем принимают
всё остальное · **Найден:** 2026-09-05 приёмкой `plans/88` Ш3.
**Класс:** зелёный, неотличимый от «не смотрели» ([[EXP-0112]]) — второй за день, после `bugs/106`.

## Симптом

`twin-assembly.mjs --rehearse-death strangle --no-window`, прогон 2026-09-05 10:11:

```
ПРОГОН: код null · лог …twin-death-strangle-2026-09-05T10-11-40-03-00.log
✅ срабатывания есть, и причина у КАЖДОГО — beat-silence (намерения в журнале судьи: 94)
✅ рука 1 отработала …
✅ полоса ПРОДОЛЖИЛАСЬ после спасения (строк «ПОЛОСА ПРОДОЛЖАЕТСЯ»: 1)
… 8 из 8 ✅ · КОД ВЫХОДА strangle = 0
```

`код null` у `spawnSync` означает **процесс убит, а не завершился** — здесь по таймауту в 300 с.
Полоса закрыла ОДНУ частоту из трёх (базовая линия того же дня: три из трёх за 7,5 с). Репетиция
объявила себя зелёной и вернула ноль.

## Причина

`mainRehearseDeath` печатает код прогона строкой отчёта и **не кладёт его в список проверок**:

```js
const r = spawnSync(process.execPath, [engine, '--sweep', …], { …, timeout: 300_000 });
console.log(`ПРОГОН: код ${r.status} · лог ${logFile}`);   // напечатано — и забыто
…
const checks = [ /* восемь проверок, ни одна не про r.status */ ];
return bad === 0 ? 0 : 1;
```

Все восемь проверок читают УЛИКИ (журнал судьи, кольцо, пульс, отпечаток I1). Улики от убитого
прогона выглядят как улики от прошедшего: срабатывания были, руки отработали, кольцо на месте.
Отсутствует единственный факт, который отличает «прогон закончился» от «прогон убили», — и он был у
функции в руках.

## Почему это опаснее обычного ложного зелёного

Этим прибором принимается всё, что касается аварийной защиты: `plans/63`, `plans/65`, `plans/66`,
`bugs/104`, и он же назван строкой РЕЕСТРА ПАР как ритуал закрытия сессии. Приказ владельца по
приёмке звучит дословно *«по коду выхода и счёту 🔴, никогда по фильтрованному grep»* — а прибор,
которым его исполняют, сам код выхода не проверял.

## Починка

Девятая проверка, первой в списке — прогон обязан ЗАВЕРШИТЬСЯ САМ:

```js
[`прогон под репетицией ЗАВЕРШИЛСЯ САМ, а не был убит (код ${r.status}${r.error ? `, ${r.error.code ?? r.error.message}` : ''})`,
  r.status !== null],
```

Проверяется именно `!== null`, а не «код равен такому-то»: у репетиции смерти ШТАТНЫЙ исход — код 1
(полоса встала на первом же шаге от стока), и требовать ноль значило бы завести второе решение о
том, какой исход правильный, там, где нужен один факт — прогон кончился сам.

**Доказано красным:** на прогоне `strangle` 2026-09-05, том самом, что вскрыл дефект, — проверка
краснеет и репетиция возвращает 1. Причина того таймаута — отдельный тикет `bugs/108`.
