# Bug 47 — сдвиг считается по ОДНОЙ таблице, а применяется к ДРУГОЙ, и карта выдаёт 910 мВ при стоке 895

**Статус:** ✅ **ПОЧИНЕН ОФЛАЙН 2026-08-24 00:2x, ЖИВОГО ПОДТВЕРЖДЕНИЯ ЕЩЁ НЕТ.**
Найден живым прогоном 2026-08-23 23:52, назван владельцем: *«подставила 910 при стоке 895 - чини»*.

## ✅ ПОЧИНКА — пара СХЛОПНУТА, а не поставлена под наблюдение

`vf-step.offsetForTarget()` — чистая функция; атом, получив ЦЕЛЬ (`targetClockMhz`), пересчитывает
сдвиг по ТОЙ ЖЕ таблице, по которой строит вектор. Движок цель передаёт (`engine.mjs`, вызов атома).

Вынесено в отдельную функцию по необходимости: у пути записи `runStep` офлайн-шва нет — это
записанный долг модуля, — а решение обязано быть допрашиваемым блоком.

⚠️ **Прямой сдвиг остался прямым.** Опыты, `--drill` и ручные прогоны цели не задают: подменять им
число было бы захватом чужого решения. Нет цели или нет частоты точки — не трогаем.

## Симптом

Прогон полосы 2355…2310 МГц встал на второй же ступени, покрытие 0 из 7:

```
ВЫДАЧА ВЫШЕ СТОКА: заказано 845 мВ на 2355 МГц, а частоту обслуживало 910 мВ
при стоке 895 мВ. Выше заводского напряжения мы частоту не поднимали
```

Заказали **глубже** (845 при стоке 895), а получили **выше стока** (910). Направление обратное
самому смыслу андервольта.

## Улика — та же ступень в двух прогонах, из журнала упреждающей записи

`runs/sweep/journal.jsonl`, seq 690–693. Прогоны разделены полутора часами; карта во втором стартовала
остывшей.

| прогон | заказ | `deltaMhz` | точка | обслужило |
|---|---|---|---|---|
| 22:07 | 850 мВ | **180** | 64 | 850 — точно |
| 23:50 | 850 мВ | **173** | 64 | **860** |
| 22:07 | 845 мВ | **210** | 63 | 845 — точно |
| 23:50 | 845 мВ | **203** | 63 | **910** |

Сдвиг в обоих случаях второго прогона на **7 МГц меньше**, и оба раза выдача уехала вверх. Это не
совпадение и не тепловой шум одной ступени: смещение systematic и одинаковое.

## Причина — арифметика, а не физика

Таблица читается **дважды, из одного источника, в разные моменты**:

1. **Движок**, `sweepRange` → `readPointsFn: () => nvapi.readVfCurve(nv, handle).points` (`engine.mjs:7437`),
   и по ЭТОЙ таблице `planRung` считает `deltaMhz = clockMhz − entry.mhz` (`engine.mjs:449`).
2. **Атом**, `vf-step.runStep` → `const curveNow = nvapi.readVfCurve(nv, handle)` (`vf-step.mjs:1531`),
   и вектор строится `buildRaiseAndCapVector(curveNow.points, deltaMhz, …)` — то есть **готовый сдвиг
   применяется к ДРУГОМУ чтению**.

Между чтениями: запись намерения с `fsync`, преднастройка атома, взвод сторожа. Секунды — а ось
частот таблицы едет с нагревом ≈ −1,7 МГц/°C (R14b).

**Куда садится точка:**

```
посадка = p63_атома + delta = p63_атома + (2355 − p63_движка) = 2355 + (p63_атома − p63_движка)
```

Карта успела нагреться между чтениями → `p63_атома < p63_движка` → посадка **ниже** 2355 → точка 63
до частоты НЕ дотягивается → 2355 МГц начинает обслуживать точка выше, с бóльшим напряжением. 910 мВ.

⚠️ **Перечитывание таблицы перед ступенью (`livePoints`) от этого НЕ спасает и не для этого делалось.**
Оно убрало дрейф между НАЧАЛОМ ПРОГОНА и ступенью (стойка 2026-08-16). Здесь дрейф живёт ВНУТРИ
ступени, между двумя чтениями, и свежесть первого чтения ничего не меняет.

## Почему это не поймал ни один сторож

Каждая половина верна по отдельности. Движок честно считает сдвиг по свежей таблице; атом честно
строит вектор по своей свежей таблице. Дефект живёт РОВНО В СТЫКЕ — в том, что это две разные
таблицы. Существующий сторож «таблица уехала» сравнивает `points` прогона со свежим чтением движка,
то есть обе половины ДО стыка, и о втором чтении не знает ничего.

## План починки

1. **Схлопнуть пару, а не следить за ней** (реестр пар: пара, которую можно УБРАТЬ, лучше пары, за
   которой надо следить). Атом обязан выводить сдвиг из ТОЙ ЖЕ таблицы, по которой строит вектор:
   передавать ему ЦЕЛЬ (`clockMhz` + `voltageMv`), а не готовое число.
2. **Пока цель не передана — сторож на стыке:** атом сверяет, что вектор, который он собирается
   писать, действительно кладёт заказанное напряжение на заказанную частоту ПО СВОЕЙ таблице. Не
   кладёт — это НЕ измерение, и ступень не жжётся (прожиг стоит минуту на карте владельца).
3. **Блок + мутация.** Фикстура, где таблица атома отличается от таблицы движка на N МГц: без
   починки выдача уезжает вверх, с починкой — садится точно. Мутация «вернуть применение готового
   `deltaMhz`» обязана покрасить блок.
4. **Сообщение об отказе называет обе таблицы** — что видел движок, что видит атом, и на сколько они
   разошлись. Сегодняшнее «несработавшая запись» описывает следствие и уводит от причины.

## Решения, принятые без владельца

- Диагноз выведен из ЖУРНАЛА прогона, а не из повторного прогона: улика уже есть, а каждый
  повторный прогон — это минуты прожига на карте владельца и риск зависания.
